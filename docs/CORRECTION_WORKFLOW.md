# QZDB 数据纠错闭环与审核流转机制规范 (CORRECTION_WORKFLOW.md)

> **入口定位**：公开纠错反馈页面位于官方站点 [https://www.qqzeng.com/ip/ip-fb.html](https://www.qqzeng.com/ip/ip-fb.html)。
> **核心原则**：
> 1. **全栈双协议支持**：支持单个 IPv4/IPv6、Range 范围、CIDR 网段提交；
> 2. **人工复核兜底**：严禁未经审核自动直接写库，杜绝恶意污染或临时代理误导；
> 3. **等同后台更新**：外部纠错经审核采纳后，处理权限与流程完全等同于管理端/UI 提交的日常人工补丁；
> 4. **4 维独立锁保护**：采纳人工补丁时，自动对命中网段打上人工锁定，防止被后续外源全量合并覆盖。

## 一、线上现有纠错入口字段契约

基于 `https://www.qqzeng.com/ip/ip-fb.html` 现网表单与接口契约：

### 1. 表单提交字段
- **`ip`**（必填）：支持标准点分十进制 IPv4、冒号十六进制 IPv6、Range 范围（如 `1.1.1.0-1.1.1.255`）、标准 CIDR（如 `1.1.1.0/24`、`240e::/32`）；前端已内置完整的双栈正则与失焦实时校验；
- **`country`**（必填）：期望国家（中文，如 中国、美国）；
- **`province`**（必填）：期望省份/州（中文，如 广东省、加利福尼亚州）；
- **`city`**（必填）：期望地级市（如 深圳市、山景城）；若网段为省级骨干/跨境链路无法下探城市，可填省份全称或空；
- **`district`**（选填）：期望区县（如 南山区、西湖区）；
- **`isp`**（选填）：期望运营商名称（如 中国电信、阿里云、腾讯云）。

### 2. 后端接收端点
- **`POST https://www.qqzeng-ip.com/api/IpFeedback`**
- 响应结构：`{ "code": 0, "message": "success" }`

## 二、工单流转与四级审核机制 (Workflow Pipeline)

```
[前端提交 ip-fb.html] 
       │ (JSON POST)
       ▼
[阶段 1: 格式与防刷网关]
       │ ── 频率限制、CIDR 范围边界校验、自动关联库内当前定位与 ASN
       ▼
[阶段 2: 证据分级与可信度判定]
       │ ── Tier 1: 运营商/企业官方书面证明或 Geofeed 声明 (极高置信)
       │ ── Tier 2: 活跃 BGP 宣告与 RIR 委派一致性佐证 (高置信)
       │ ── Tier 3: 普通用户单点定位反馈 (普通线索，需多点聚合)
       ▼
[阶段 3: 专业数据团队人工复核]
       │ ── 采纳：等同于管理后台人工提交更新，生成标准补丁
       │ ── 驳回/挂起：记录驳回原因（如与 BGP 宣告冲突、证据不足）
       ▼
[阶段 4: 版本化合流与锁保护]
       │ ── 写入数据库维度层表 (source='manual', confidence=100)
       │ ── 物理翻转 4 维人工锁 (is_manual_geo / is_manual_isp 等)，永久锁死防冲刷
       ▼
[阶段 5: 下期月度全量发行 (次月 1 日)]
       └── 纳入 CHANGELOG，随当期 QZDB 与 CSV 交付
```

## 三、高风险网段人工复核红线

对命中以下特征的纠错申请，**必须触发专家级二次交叉复核**，严禁单人快速放行：

1. **国家级/主权冲突网段**：涉及境外跨区、APNIC/RIPE 跨境委派冲突段，必须核实 WHOIS 与现网 BGP 活跃广播路径，非 `CN` 严禁违规归入国内；
2. **大容量骨干块（$\ge /16$ IPv4 或 $\ge /32$ IPv6）**：严禁因局部机房或单点测速将整个大段强行钉死到某一地级市；
3. **复合/专线 ISP 记录**：针对已包含穿透互联、骨干多线心血（如 `中国电信/CN2`、`百度云加速/移动`）的网段，严禁用单一 ISP 进行一刀切覆写。
