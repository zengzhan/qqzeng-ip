# QZDB 对外文档排版规范(Document Style Guide)

> 适用于发布仓全部 README 与对外文档。目标:**窄屏(手机/半屏)可读、一眼抓到重点、
> 每个数字可验证**。核心原则一句话——**表格窄、段落短、深内容折叠、数字带口径**。

## 一、表格纪律(最常见的"挤"源)

1. **≤4 列,单元格 ≤25 个汉字**:挤的根源是"多列 × 长文本单元格"组合——
   全短单元格(≤8 字,如版本号/体积)可放宽到 6 列。长内容进脚注、进折叠区、
   或拆成表格下方的小节。禁止在单元格里用 `<br>` 堆多行段落。
2. **链接并入锚文本**:语言名/产品名本身就是最好的链接位,不要为链接单开一列
   (安装命令已有专门章节时,"获取方式"列完全冗余)。
3. **数字右对齐**(`---:`),文本左对齐,表头不换行。

正反示例(性能榜单):

```markdown
<!-- ✅ 好:4 列,链接并入语言名,单元格极短 -->
| 语言 | 整型查询¹ | 字符串查询 | 特点 |
| :--- | ---: | ---: | :--- |
| 🔥 [Node.js](./ip-qzdb-sdk/nodejs) | **99.4 M/s** | 5.5 M/s | JS 生态最快档 |

<!-- ❌ 坏:7 列,链接独占一列,延迟/评价/获取挤在一起 -->
| 排名 | 语言 | 口径A | 口径C | 延迟 | 评价 | 获取方式 |
```

## 二、结构节奏

1. **首屏三件事**:一句话定位 + 性能榜单(或亮点)+ 30 秒安装。理论/架构放后面。
2. **每节一个信息单位**:一个 `##` 只讲一件事;发现要"顺便讲"时,另起一节或给链接。
3. **深内容折叠**:`<details><summary>` 用于——机制细节、口径定义、注脚、
   次要语言的代码示例。折叠区内的首行 summary 必须自描述("点开查看"式措辞)。
4. **目录**:超过 150 行的文档必须有 TOC(锚点链接)。
5. **代码块必须标语言**,示例必须可跑(含加载语句,不许只给查询片段)。

## 三、数字书写(与 PERFORMANCE.md 联动)

1. **三要素**:数值 + 口径(A 整型随机 / B 热点 / C 字符串,见 docs/PERFORMANCE.md)+ 复现入口。
2. **承诺用最不利**(口径 A),热点数字(口径 B)只能作为补充出现,不得单独引用。
3. **单位统一**:≥1M 写 `99.4 M/s`;万级写 `5.67 M/s`;千级写 `429 K/s`。不用"万"与"M"混排。
4. **环境声明**必须出现在数字附近(硬件 + 单线程/多线程),或收进口径折叠区。

## 四、语言与语气

1. 中文文档用简体中文,术语首次出现给英文(Memory Mapping(mmap));英文文档用美式拼写。
2. emoji 只作**视觉锚点**(每语言/每产品一个固定 emoji,全仓库一致):
   🔥 Node · 👑 C · ⚡ Go · ☕ Java · 🛡️ Rust · 🚀 C# · 🐘 PHP · 🐍 Python。
3. 不用营销形容词堆砌("极致""极速""碾压")——用数字与限定语说话;
   允许的强度上限是「最快档」「生产推荐」这类**可被数字支撑**的短语。
4. 禁止:无口径裸数字、跨语言挪用数字(C 的数字不得为 PHP 背书)、只有最好情形。

## 五、自检清单(提交对外文档前过一遍)

- [ ] 所有表格 ≤4 列,单元格 ≤25 字?
- [ ] 深内容/注脚已收进 `<details>`?
- [ ] 每个性能数字带口径与复现入口?
- [ ] >150 行的文档有目录?
- [ ] 在手机宽度(或浏览器窗口拖到 1/3)预览过一遍?
