## 三、新一代 QZDB (`.qzdb`) 8 语言全口径基准评测

不同于传统格式要么“只返回单行竖线字符串（需调用方二次切割）”、要么“像 MMDB 一样每次查询都在堆上动态反序列化嵌套 Map”，**QZDB 通过 `16-bit Jump Table + 扁平化 PATRICIA Trie + RowSchema 物理偏移表`**，在**直接返回 6~25 维结构化字段**的前提下，依然保持了与纯偏移格式同量级甚至更高的吞吐能力。

| 语言与工程阵营 | 口径 A：单核整型随机 | 口径 B：单核热点 / 16核并发 | 口径 C：字符串直查 `find_str` | 核心技术特性 |
| :--- | ---: | ---: | ---: | :--- |
| 👑 **[C / C++](../ip-qzdb-sdk/c/README.md)** | **96.5 M/s** | 101.8 M/s / **506 M/s** | **12.6 M/s** | 纯 C99 零拷贝 `mmap`，栈上实例化，零堆分配 |
| ⚡ **[Go](../ip-qzdb-sdk/go/README.md)** | **97.3 M/s** | 105.5 M/s / **719 M/s** | **12.1 M/s** | 跨平台 `mmap` 只读视图，Goroutine 无锁线性扩展 |
| 🛡️ **[Rust](../ip-qzdb-sdk/rust/README.md)** | **82.6 M/s** | 88.0 M/s / **233 M/s** | **11.5 M/s** | 值语义去共享化 + 4 路组相联缓存 + `Arc<str>` 池化 |
| ☕ **[Java](../ip-qzdb-sdk/java/README.md)** | **48.1 M/s** | 105.4 M/s / **136 M/s** | **11.9 M/s** | `MappedByteBuffer` 堆外内存视图 + 零分配 IPv6 解析，0 GC |
| 🚀 **[C# (.NET)](../ip-qzdb-sdk/netcore/README.md)** | **46.9 M/s** | 132.1 M/s / **550 M/s** | **20.9 M/s** | 原生指针内存映射，字符串全链路解析吞吐第一 |
| 🟢 **[Node.js](../ip-qzdb-sdk/nodejs/README.md)** | **8.22 M/s** | 7.64 M/s *(裸循环 99.4M)* | **10.3 M/s** | V8 `BigInt` 偏移计算，纯 JS 零 C++ 扩展依赖 |
| 🐘 **[PHP](../ip-qzdb-sdk/php/README.md)** | **5.67 M/s** | 0.73 M/s *(FPM/Swoole)* | **470 K/s** | 纯 PHP 零扩展，支持全内存 Buffer 与有界多页 LRU 流式模式 |

> 📌 **口径与库规模说明**（详见 [`PERFORMANCE.md`](./PERFORMANCE.md)）：
> - 口径 A 基于 50 万随机散布 IP 与省级库（8.6MB）；在 122MB 超大全球库上，受 CPU L3 缓存容量物理规律制约，各语言随机吞吐普遍回落约 3 倍（如 Go 23.9M/s、C 13.7M/s），仍远超毫秒/微秒级业务需求。

## 五、为什么 QZDB 能同时兼顾「25 维结构化字段」与「千万级 QPS」？

传统认知中，“高吞吐（如 `.dat`/`.db` 纯字符串偏移）”与“丰富结构化多字段 + IPv6 双栈（如 `.mmdb`）”往往不可兼得。**QZDB (`.qzdb`)** 通过四项核心工程创新打破了这一权衡：

| 架构设计维度 | `MaxMind (.mmdb)` | `ip2region (.xdb)` | `qqzeng 经典版 (.dat / .db)` | 🚀 **新一代 `QZDB (.qzdb)`** |
| :--- | :--- | :--- | :--- | :--- |
| **1. 首阶段索引跳级** | 无（从第 1 位逐层遍历 32/128 层） | 256×256 向量索引定位区间起止 | `.dat` 256 桶 / `.db` 65,536 前缀表 | **65,536 槽位 Jump Table (IPv4) + 自适应跳转表 (IPv6)**，$O(1)$ 跳过前 16~20 层遍历 |
| **2. 二阶段树/区间检索** | 标准逐位二叉 Trie | 局部有序区间二分查找 $O(\log N)$ | `.dat` 桶内二分 / `.db` 24-bit 二叉树 | **紧凑 PATRICIA Trie（最长前缀匹配）**，跳过公共前缀位，节点扁平连续对齐 CPU 缓存行 |
| **3. 叶子数据存储与解码** | 嵌套 Map/Array TLV 编码，**每次查询动态反序列化**，触发 GC 分配 | 定长/单行竖线拼接字符串，仅适合固定少量字段 | 单行竖线拼接字符串，调用方需手动 `split('|')` | **全局 `RowSchema` + 去重 `IPRow` 定长偏移数组**：无需反序列化，按列号 $O(1)$ 直取字符串池切片 |
| **4. 压缩算法与文件体积** | 树节点较大，多语言 Map 键名重复开销高 | 仅存 5 个基础字段，扩展至 25 维时体积剧增 | `.dat` 受 24-bit（16MB）字符池寻址上限约束 | **拓扑后序离线去重（Hash-Consing）+ 字典池化**，2.94 GB 双栈 25 维 CSV 压缩至 **69.1 MB（42:1）** |

## 六、业务场景选型总结
